# 001 — 자율 운영 에이전트 군단 설계 (D6, 초안 v1)

> 엔드게임: **"대화로 회사를 운영"을 넘어 "대화 없이도 알아서 굴러가는 회사".**
> 롤별 AI 에이전트가 일상 업무를 돌리고, 사람(CEO)은 방향 결정·예외 처리·승인만.
> 이 문서는 살아있는 초안 — 단계별 구현하며 계속 다듬는다.

---

## 0. 핵심 철학 (왜 이렇게 나누나)

- **로직 = 손/계산기 (정확성)** · **AI = 머리/통역 (이해·판단)**.
- **AI는 절대 숫자를 만들지 않는다.** 모든 수치는 도구가 장부에서 꺼낸 값만 사용 (환각 가드레일).
- **결과가 큰 행동(돈·외부발송·채용)은 AI가 준비만, 마지막 클릭은 사람.**
- **권한이 곧 롤의 경계.** 각 에이전트 = 권한 가진 User로 실행 → 도구가 자동으로 권한 준수.

- "엔지니어" → **IT·자산**으로 재해석 (순수 엔지니어링은 ERP 밖; 자산대장은 회계 직결).
- **구매·재고 롤은 필수** (하드웨어 회사 — 벤더·PO·입고가 회계의 입력).
- 자금(Treasury)은 초기엔 회계에 합침; 규모 커지면 분리.
- CEO 비서 에이전트 불필요 — CEO가 아무 롤한테나 대화로 질의 (현 assistant가 그 역할).

## 2. 오케스트레이션 — 작업큐 + 디스패처

```
인입(메일/업로드/명세서/대화지시) → [디스패처] 분류
   → tasks 테이블에 (받을롤 + 내용 + 상태=대기) 적재
각 롤은 자기 루프 때 → 자기 큐의 '대기' 건만 집음
   → 처리  /  "내 거 아님 + 이유"로 반송
   → 반송 3회↑ 핑퐁 시 CEO 에스컬레이션
결과 큰 행동(지급·발송) → '승인대기'로 CEO에게
```

- **작업큐 테이블:** `tasks(from_role, to_role, payload, status, bounce_count, created_at)`
- **상태 도장(= 중복방지/idempotency):** 대기 / 처리중 / 완료 / 승인대기 / 반송
  - 주간 루프가 또 돌아도 **이미 처리된 건 안 집음** (status로 필터).
- **반송(bounce-back):** 잘못 배정 시 사유와 함께 디스패처로 반송 → 재분류. 사유는 라우팅 로그로 남겨 분류 정확도 개선.
- **모든 행동 = audit 로그** (이미 구현됨).
- **결정(D6): 스케줄러 = APScheduler (인-프로세스).** FastAPI 앱 안에서 같이 돌며
  "10분/일간/주간/월간" 작업 등록. 외부 의존성·별도 서버 없음 (단일 로컬 어플라이언스에 최적).
  규모 커지면 별도 워커 프로세스로 분리 가능.

### 인입 채널
출처 무관 — 디스패처엔 전부 "처리할 일 하나":
- 📧 연결된 이메일 · 📎 업로드 파일 · 🏦 은행 명세서·스캔 · 💬 CEO 대화 지시.
- 전부 같은 분류기 → 같은 작업큐. 채널만 다르고 이후는 동일.

## 3. 루프 주기 (4종)

| 주기 | 트리거 |
|------|--------|
| 10분 | 반응형: 새 메일·문서·요청 처리 |
| 일간 | 자산 점검, 미처리 잔무 정리 |
| 주간 | 💸 **결제목록** 작성 → CEO, 주간 요약 리포트 |
| 월간 | 마감(클로징 패키지), 전월 대사 검증 |

### 주간 결제 흐름 (payment run — SAP F110 패턴)
```
[주간 루프] 미지급 청구서 모아 "이번 주 결제목록" → CEO
[CEO] 실제 은행에서 송금 → "결제 완료" (목록에 항목별 확정)
[회계] 최종 분개 (Dr 외상매입금 / Cr 현금)
[은행 명세서 입수] 자동 대사로 "진짜 나갔는지" 검증  ← 장부가 스스로 감사됨
```
- "다했어" 한마디 대신 **어떤 청구서를 얼마 냈는지 항목 확정** → 분개 정확도 + 은행 대사 자동검증.

## 4. 자동 vs 사람 승인 경계

| AI가 끝까지 (자동) | 사람 승인 필요 |
|------------------|--------------|
| 분류·라우팅·정리·드래프트 | 💸 **모든 실제 지급 (금액 무관, 예외 없음)** |
| 인보이스→청구서 **초안** | 📤 외부 메일·계약 발송 |
| 은행 대사 **제안** | 👤 채용/해고 |
| 리포트·질문 답변 | ⚠️ 비가역·고액 결정 |

> **결정(D6):** 지급은 **금액 기준 없이 전부 CEO 승인.** AI는 결제목록·분개 초안까지만, 자동 지급은 절대 없음. (가장 안전한 기본값 — 신뢰 쌓이면 후일 재검토)

## 5. 보안 모델 — "우리 데이터는 절대 밖으로"

### 2대 원칙
1. **🔒 회사 데이터는 절대 외부로 안 나간다** (숫자·이름·계약 — 한 바이트도).
2. **🌐 모르는 건 바깥에서 "지식"만 가져온다** (웹검색 / 프론티어 자문).
   - 충돌 안 함: 바깥에 보내는 건 **"방법·사실 질문"이지 회사 데이터가 아님.**

### API 두 종류 — 방향이 전부
| 종류 | 방향 | 위험 |
|------|------|------|
| 클라우드 AI API (OpenAI/Gemini/Claude) | 📤 내 데이터가 나감 | 🔴 진짜 위험 — 001은 **안 씀** (로컬 Qwen) |
| 데이터소스 API (Gmail/은행/QBO) | 📥 내 데이터를 가져옴 | 🟢 안전 — 내 것을 로컬로 내려받아 로컬 분석 |

→ **"로컬 LLM"은 이메일·QBO 연결해도 안 깨짐.** 분석은 로컬, LLM은 인터넷 안 함.

### "API냐 브라우저냐"는 무의미 — 가르는 건 "무슨 데이터가 나가느냐"
- 브라우저로 ChatGPT 웹창에 회사자료 타이핑 = API와 **똑같은 유출** (소비자 웹은 학습까지 — 더 나쁠 수도).
- 브라우저의 안전·유용한 용도 = **공개 정보를 IN으로 읽기** (웹검색·세율·뉴스). 검색어만 나감.

### 모르는 걸 만났을 때 에스컬레이션
```
1. 로컬 먼저   → 도구·회사규정(RAG)에 답 있나
2. 웹 검색     → 공개 사실/최신 정보 (검색어만 나감)
3. 프론티어 자문 → Claude/GPT에 "방법"만 (데이터 0, 사람 검토 후)
   ※ 어느 단계든 회사 데이터는 outbound payload에 안 실림
예) ⭕ "복식부기에서 AP 보조원장 0, GL 통제 1.6M이면 원인·대사법?"
    ❌ "우리 $1.6M AP가 왜 안 맞아?"
```

### 강제 — 프롬프트 규칙만으론 부족, 기술적 울타리 병행
1. **구조적 격리** — 회사 데이터 만지는 부분은 인터넷 접속 없음. 외부로 나가는 건 좁은 "외부질의" 컴포넌트 하나.
2. **송신 검문(egress guard)** — 나가는 요청에 회사 데이터 섞이면 차단/마스킹.
   **결정(D6) 탐지 범위 = "DB 실체 + 패턴" 이중:**
   - DB에서 뽑은 실명 목록 — 벤더·고객·직원 이름, 계정명 (실데이터라 가장 확실)
   - 패턴 — 달러 금액(`$1,656,263`), 계좌번호, EIN/사업자번호, 이메일주소
   - → "방법 질문"엔 안 걸리고, 회사 데이터가 섞이면 걸림.
3. **사람 승인** — AI는 외부 질문 **초안만** → 사람이 보고 전송.

### 이메일 커넥터 (외부로 나가는 유일한 문)
```
[인터넷] ──TLS──> [이메일 커넥터]  ← 유일한 외부 통로(읽기전용·감사로그)
                        ↓ 가져온 메일
[4090/LLM/회계엔진/DB]  ← 전부 오프라인, 인터넷 0
```
- **결정(D6): 회사 메일 = Google Workspace.** 커넥터 = **Gmail API + OAuth 읽기전용**
  (드래프트는 Gmail API로 저장). IMAP+앱비번은 초기 프로토타입 한정.
- 클라우드 메일이므로 "완전 오프라인"은 메일 가져오는 순간만 양보 — 단 **분석은 로컬,
  내 메일을 로컬로 내려받는 것**이라 보안상 유리 (§5 방향론).
- 토큰은 `.env`(gitignore)/OS 키링에 암호화. **발송 자동 금지 — 드래프트만.**
- 메일 본문 = 신뢰 안 함 (프롬프트 인젝션 방어, 현 규칙 8 적용).

## 6. 하이브리드 지능 — 로컬 최신 유지 압박 해소

- **로컬:** 일상 실행 (데이터 처리) — 정확·안전.
- **프론티어 on-demand:** 어려운 문제의 **방법론 자문** (데이터 없이, 사람 경유 우선).
- **로컬 모델 업데이트:** 공짜·쉬움(weights 교체). **최신 추격 "압박"에서 해방**되는 것이지 영원히 고정은 아님 — 좋은 게 나오면 가끔 올림.

> 프론티어 = 우리 장부 못 보는 **컨설턴트**(방법 제공). 로컬+엔진 = **실무자**(실데이터 실행).

## 7. 진행 방식 (단계적 — 한 번에 7명 금지)

- **1단계:** 디스패처 + 회계 **2명.** 작업큐 + 처리 루프 검증. 이메일·반송 없이.
  **결정(D6) 1단계 입력 = 둘 다:** ⓐ 업로드 문서함(인보이스·명세서) + ⓑ CEO 대화 지시.
  (외부 이메일은 3단계에서 합류)
- **2단계:** 반송·에스컬레이션 추가 → 구매·HR 합류 (4명). 롤 간 핸드오프 검증.
- **3단계:** 이메일 커넥터 + 주간 결제 루프 (외부 I/O 등장).
- **4단계:** 정책·자산 롤 + 월마감 자동화 → 7명 완성.
